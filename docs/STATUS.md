## Главное, что нужно знать

**Проверено автотестами (137 тестов, eval 64/64):** слоты, запись, защита от двойной записи, планировщик, тихие часы, guardrails, маскирование ПД, RLS, диалоговые сценарии. Всё это прогонялось на локальном Postgres и **детерминированном движке** (без LLM).

**Ни разу не запускалось вживую** (в среде разработки не было ни сети наружу, ни ключей, ни Docker-демона):

- Claude через Anthropic API (код tool-use цикла написан, с реальным API не проверен);
- Telegram Bot API и Telegram Business (адаптер написан, запросов в реальный Telegram не было);
- WhatsApp: Baileys-сайдкар (проверен только `node --check`, `npm install` и QR не выполнялись), Cloud API;
- `docker compose up` (файлы написаны, `docker compose config` и сборка образов не выполнялись);
- платёжные провайдеры, STT.

Поэтому «демо за одну команду» — это **гипотеза, которую надо проверить первым делом** (задачи P0-1…P0-4 в TASKS.md).

## Известные ограничения и риски

1. **Запуск в Docker не проверен.** Роль `arix_app` теперь создаёт `scripts/init-db.sh` (пароль уходит в psql через `-v`). Права этой роли на таблицы миграции на живом `docker compose up` всё ещё не смотрели.
2. **Ядро выровнено с `edu-ai`.** Детерминированный диалог — общее ядро плюс `ClinicPlaybook`. Общие файлы `agent/scripted.py`, `agent/brain.py`, `agent/runtime.py` и планировщик совпадают байт-в-байт. Проверено 137 тестами на детерминированном движке.
3. Бот-личность: промпт не называет бота человеком, но и не раскрывает «я ИИ» без вопроса. Если заказчик хочет иначе — это одна строка в `agent/prompt.py`.
4. Для WhatsApp через Baileys остаётся риск блокировки номера (см. WHATSAPP_BAILEYS.md); решение принято заказчиком осознанно.
